# rc.10：在原滑点保护内分批恢复残余仓位

当平仓首腿已成交、另一腿明确零成交，而剩余数量无法一次穿过受保护的盘口深度时，旧版会等待整笔深度恢复。rc.10 允许仅对这次操作已确认的 Entropy 残余数量分批执行 reduce-only 补偿。每批按平台数量精度向下取整，确认终态、核对账户和账本后才发下一批；未知订单始终只查原单。Lighter 的最小订单限制、普通开仓和第二腿下单的完整深度校验保持原规则。

不修改开仓信号、30 分钟同价加仓、5U 网格、每档最多 5 次、原滑点参数和旧仓归属。分批补偿不保证网络中断或没有可成交深度时一定立即完成；这些情况下继续禁止新交易并保留告警。

## 其他修复

- Entropy 账户恢复所需的四项只读查询并行执行，减少串行请求造成的超时。
- 双平台核对完成后，若快返回的一侧已经过期，只刷新该侧；次数和总时间有上限，不放宽账户时效要求，不伪造时间戳。
- 监控页在一次处理完成后发布最新行情，避免把账户请求之前的旧盘口再次显示为当前盘口。
- 通知队列恢复可读后清除过期的队列错误；不会因为仅查询成功就清除仍在重试的飞书发送失败。

## 现场升级

先停止两个标的的策略并保持后台打开，运行原有一键诊断。若仍有未完成操作，先依据最新诊断确定原订单终态及进度，使用针对该现场的退出步骤。不要清空 pending、修改数量或手动补单来满足升级条件。

后台完全退出后，备份完整旧目录（包含 SQLite、WAL 和密钥库），再把完整 data 复制到新的程序目录。核对版本、提交号、运行模式和实际数据目录后，分别解锁并加载原账本。加载可能继续未完成操作的受控配平；不要启动新的策略交易。再次运行诊断，确认真实账户与账本一致、无未完成操作和孤立仓位后再启动。

Mac 与 Windows 使用同一 Rust 执行核心；测试仅使用合成账户和本地模拟服务，不连接真实交易账户。

## 回归覆盖

- 用旧执行代码复现受保护深度不足时无法推进的场景，及通知队列已恢复但错误仍显示的场景；应用修复后相应测试通过。
- 合成 990 单位持仓、首腿已平 180 单位的故障，按 60、60、60、20 单位发出四批请求，第一批仅成交 40；逐批关闭并重开真实 SQLite 文件，验证总计仅补偿 180 单位，旧的九组持仓不变。
- 上述场景覆盖 OPENAI、ANTH 和两个方向，检查重复回执不重复计数、平台步长、原滑点、请求标识唯一，以及停止交易标志保留。
- 账户核对测试覆盖单侧过期后刷新、持续过期和未来时间戳；超过次数上限即停止本次核对，不提交订单。
- 继续运行既有未知订单、超额成交、所有 pending 阶段阻止新开仓、订单截止时间、资金费、通知延迟/取消和签名向量回归。

构建验收以对应 GitHub 工作流的 Windows 和 Mac 结果及 `shared-core-verification.json` 为准。本机测试通过不代表 Windows 实盘已经修复；需要部署后再次核对。
