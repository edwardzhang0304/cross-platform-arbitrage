# 多平台套利：标准故障排查与处理流程

适用于同一个 Windows 后台管理 OPENAI、ANTH 实盘。Mac 与 Windows 继续使用同一份 Rust 策略核心。

## 出问题时，你只需要做什么

1. 保持后台打开。在正在使用的 EXE 旁双击 **Run-Diagnostics.cmd**。它通常在半分钟左右结束；网络或账本繁忙时可能更久。
2. 把桌面生成的 **CPA-Diagnostics-日期时间-编号.zip** 发来，同时用一句话说明看到的现象、是否手动交易/修改网络/重启过。无需复制多轮命令，也不用发送整个 data。
3. 如果要阻止新增开仓，在两个标的配置页分别点击“停止交易”。停止策略仍允许保护性恢复已有未完成订单；不要把停止交易理解为立即终止所有账户请求。

命令行等效操作：在程序文件夹的 PowerShell 中运行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Read-Diagnostics.ps1
```

后台打不开也可以双击同一个入口，脚本会使用旁边的 data 做只读检查。程序使用其他端口或数据目录时：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Read-Diagnostics.ps1 -Port 18794 -DataDirectory 'D:\你的程序\data'
```

目录名称可以自由命名；是否为新版依据实际进程、版本、提交号和 EXE 哈希判断，不依据文件夹必须含 rc9。

## 诊断包包含什么

- 程序版本、提交、运行模式、策略核心哈希、实际 EXE 路径/哈希、使用中的数据目录。
- OPENAI 和 ANTH 各三次状态观察：真实账户、账本数量、未完成订单、恢复计数、行情及账户时间戳、通知状态。
- 未完成操作的首腿、对冲腿、补偿、精度对齐及尾数回补阶段，创建/过期时间、确认数量、终态及重试时间。
- 每个账本最近的关键事件；当前异常操作创建前后的一段历史。只读查询最多 120 条/2 秒，超限、缺失或失败明确标注。
- 当前持仓及异常时间窗口内已记录的成交；订单标识用稳定摘要关联，不导出地址和账户凭据。
- 系统时间同步状态、磁盘空间、两个公共接口的 HTTP Date/耗时参考。HTTP Date 受 CDN 缓存影响，不能单独当作精确校时依据；系统网络参考也不等于交易工作线程的私有接口延迟。

只生成 report.json 和说明.txt 的 ZIP。**不导出密钥库、钱包地址、账户配置原文件、CSRF、飞书凭据或原始数据库；不自动上传。** 查询使用系统 winsqlite3 的只读模式和只读 SQL 校验，不写交易账本。输出文件含持仓和交易信息，仍应只发给可信的排查人员，不要提交到公开 GitHub。

“未加载”“查询失败”“过期证据”与“零持仓”严格区分。API 和磁盘观察不是交易所原子快照，必须结合时间戳判断。事件窗口被截断或平台证据不可用时，仍可能需要一次针对性补查。

## 收到诊断包后的固定处理顺序

1. **先确认身份和证据有效性**：实际 EXE/提交/模式、数据目录、是否多个进程或打开旧页面、时间同步、行情/账户证据是否新鲜。
2. **比较数量**：逐边核对真实账户与账本；pending 存在时不能仅按持仓组数判定损坏，已成交首腿会暂时大于配对仓位。
3. **定位订单阶段**：区分“签名前未提交”“平台明确终态”“提交后结果未知”。结果未知只查询原订单，不能因为页面没有挂单就认定零成交后重发。
4. **核对恢复前提**：原请求终态、实际数量和归属、挂单、保护价格、数量精度及退避时间；不通过就保留现场，不手动清 pending、改数量、放宽滑点或用旧备份覆盖当前账本。
5. **必要时修复程序**：先用合成证据重放故障，验证不会重复发旧单、不会动到无关持仓，再做 Mac/Windows 两模式测试、签名及 Windows 启动检查、共享核心一致性验收。
6. **恢复后验收**：逐边真实数量=账本，配对持仓数量正确，无 pending/孤立仓位/挂单，资金费完整，策略规则与飞书配置正确。再检查连续回滚、止损等保护，按控制台允许的流程重新启动。

通知到达不代表程序停止执行保护性恢复；修复包通过测试也不等于 Windows 现场已经恢复。最终以新鲜账户证据和账本完成状态为准。

## 升级与备份

常规升级：新包解压到新目录 → 两个标的停止 → 诊断确认无未决操作 → 正常退出后台 → 备份完整旧目录 → 完整 data 复制到新 EXE 旁 → 核对版本并加载 → 验收后启动。

有未知订单时不使用常规升级流程。若确需带 pending 修复，必须先核对请求期限和原订单证据，按现场专门步骤关闭已确认 PID、保留全部账本和 WAL 后升级，不能为了退出而清空状态。

恢复发生真实成交后，旧备份已不是当前账本，不能直接恢复旧备份继续交易。

## 飞书通知规则（rc.9）

- 双腿成交、补偿、对齐或查询异常首次出现后，先等待 **60 秒**。同一订单进入“需要处理”不会重置计时或绕过等待。
- 等待期内恢复，全程静默；恢复后取消尚未发送的异常消息，不单独发送“配平成功”。
- 超过 60 秒仍未恢复才通知。同一持续异常最多每 5 分钟提醒一次，断网时只保留一个待发提醒，不堆积同一事件。
- 等待时间和事件关联持久化，重启不重置；无新行情/账本提交时，独立通知定时器仍会检查到期事件。
- 发送前再次确认通知未被恢复流程取消。已经发往飞书的请求无法撤回，恢复与网络发送恰好同时发生时可能仍收到一条在发送时有效的告警。
- 独立的账本写入失败、确认孤立仓位和总亏损保护仍立即通知。飞书失败不能阻塞交易线程，也不能代替账户和账本检查。
