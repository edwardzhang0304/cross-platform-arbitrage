# rc.6 候选：执行保护与飞书异常通知

本次修改使用同一份 Rust 执行核心。OPENAI、ANTH 的网格、同价加仓、均线、止盈、滑点和仓位上限均未调整。没有连接真实账户、下单或操作 Windows 上正在运行的程序。

## 执行问题

1. **Lighter 请求取消后 nonce 卡住**：发送前取得的编号改由作用域守卫管理。签名前返回或出错时释放；一旦可能发出请求，超时取消、断开或错误都要求向交易所刷新编号。原订单仍由持久化订单 ID 查询，不能因为刷新编号而重发原订单。
2. **停止后仍发出已排队的开仓**：暂停、停止和全部平仓会取消没有任何请求标记、没有任何成交的开仓意图。已经发送或结果未知的订单不能删除，继续按原流程查询、配平或受控回滚。执行入口再次检查这些控制标志。
3. **关闭时读到旧状态**：控制命令确认前更新状态视图；真正退出 worker 时，再由交易 actor 检查已经停止、没有待处理订单及异常仓位。退出整个程序也检查并关闭另一标的的 actor。
4. **通知与防御控制互不等待网络**：通知 HTTP 在独立任务内；暂停、停止、全部平仓不等待另一标的的全局配置锁。通知请求卡住时，页面上的防御控制仍可使用。当前正在执行的交易请求仍按原有超时边界处理。

两交易所没有原子成交机制。首腿成交与第二腿成交之间可以短暂不配平；交易所拒单、断网、行情不足时，也无法保证立即消除暴露。核心约束是：结果未知时只查询原订单，禁止重复提交；补偿只处理已确认归属于该操作的数量；保留原仓位账本及保护价约束；无法安全完成时阻止继续增加风险并告警。

## 通知覆盖与可靠性

- 开仓、加仓、平仓出现未知订单结果、零成交、部分成交、补偿、精度对齐、行情中断或需要人工处理时发通知。
- 消息包含标的、模式、操作、已确认数量和事件时间，不含地址、API 密钥、原始 HTTP 错误或响应。
- 正常首腿与第二腿之间的短暂状态不单独告警；异常升级时另发提醒。同一未解决异常在状态持久化时最多每 5 分钟再提醒一次。
- 订单账本恢复配平后发结果通知，明确这不代表策略已重新启动，仍以控制台账户核验结果为准。
- 告警与交易状态同事务写入 SQLite 的独立通知表。独立发送任务每 2 秒检查，HTTP 单次最长 8 秒，连接最长 3 秒。失败按 5、15、60、300 秒退避，后续保持 300 秒。
- 使用稳定 UUID 重试同一通知，由飞书接口协助去重。网络超时后不能承诺绝无重复消息。
- 队列最多 512 条；超过时丢弃最旧记录，控制台和后续通知显示累计数量。此上限只影响通知，不删除成交或持仓。
- 账本写入失败时另留一条内存应急告警，独立尝试发送。磁盘持续故障并伴随进程退出时，这条内存告警无法保证恢复。
- 程序退出、睡眠、断电、持续断网或飞书服务不可用时，不能即时通知。落盘消息在重新加载账户、解锁通知配置后重试。

## 配置隔离

每个标的分别配置。本次部署按用户要求，仅私聊发送给张文涛本人；两个标的使用同一个机器人和经过确认的本人 `open_id`，不能仅凭姓名选择收件人。通知配置单独加密，不更改交易私钥或账户绑定：

| 标的 | 文件（相对于程序 data 目录） |
| --- | --- |
| OPENAI | `keys/feishu.vault` |
| ANTH | `profiles/anth-live/keys/feishu.vault` |

使用该标的现有密钥库密码加密，算法沿用 Argon2id + XChaCha20Poly1305；通知与交易密钥库使用不同认证域，不能互换。App Secret 不进入 Git、页面状态接口、日志或告警正文。通知默认关闭；模拟盘无真实通知凭据，但使用相同的异常检测与队列代码。

## 新版通过验收并更新 Windows 后的设置

1. 打开 **OPENAI 实盘配置**，解锁原密钥库。
2. 在 **4. 飞书异常通知** 展开配置，只在本机填写 App ID、App Secret。
3. 保持默认的“私聊（open_id）”，填写该应用下经本人确认的 `ou_…` 接收 ID。不能填写姓名、App ID 或 Webhook URL。
4. 点击 **加密保存本标的通知**，再点 **发送测试通知**。必须确认手机确实收到；HTTP 接口接受消息并不等于手机已经弹出推送。
5. 到 **ANTH 实盘配置**重复保存与测试。两个标的分开配置，避免继承错误接收目标。
6. 启动程序后应看到通知已启用；若显示失败、未解锁或待发积压，先检查通知配置。

机器人需启用机器人能力、具备发送消息权限、发布到所属租户，并将本人包含在机器人可用范围内。实现使用飞书官方[自建应用令牌接口](https://open.feishu.cn/document/server-docs/authentication-management/access-token/tenant_access_token_internal)及[发送消息接口](https://open.feishu.cn/document/server-docs/im-v1/message/create)，生产地址固定为 `open.feishu.cn`，禁止自动跟随重定向。

## 验证状态

这是候选代码，尚未替换 Windows 实盘。测试只用合成数据、隔离临时账本和本机假飞书 HTTP 服务。收件人已确认为张文涛本人，具体 `open_id` 仍待核对，尚未发送真实通知。用户已明确要求仓库保持公开，源码及无凭据的构建产物按此要求发布，任何真实凭据都不上传。

本地验证：实盘构建 292 项通过、模拟盘构建 273 项通过、签名测试 248 项通过、前端 17 项通过；两个构建各跳过 1 项公开网络探测。Mac 上实盘构建和模拟盘构建的 96 个合成策略观测、参数及核心哈希完全一致。这不等于已经完成 Windows 原生验收。该次本地结果见同目录 `rc6本地验证.json`；最终发布以对应提交的 Mac/Windows 云端回归、Windows 打包程序无凭据冒烟测试和跨平台一致性验收全部通过为准。

## P1 修复与验收对应关系

| 原审计问题 | 修复位置 | 合成回归覆盖 |
| --- | --- | --- |
| 请求取消导致 Lighter nonce 永久占用 | `lighter_runtime.rs` 的作用域守卫、`live.rs` 的提交入口 | 异步提交被取消后必须刷新；确定未发送时释放；确认成交或未成交后允许下一笔；溢出时禁止派发 |
| Stop/Pause/CloseAll 后仍执行尚未发出的开仓 | `service.rs` 的控制处理、`execution.rs` 的最终执行检查 | OPENAI/ANTH 的未发送开仓被取消且发送次数为零；任一请求标记或成交数量存在时均不得丢弃；已发送订单继续按原 ID 恢复 |

这些修复不等于跨交易所能够原子成交，也不表示此前审计中的全部 P2 问题都已解决。旧 Windows EXE 不会自动获得本次修改。

首次 Windows CI 暴露了旧离线回放夹具的时钟混用：虚拟交易所用回放时间，外层派发检查却用系统时间，慢速磁盘写入可能让历史测试订单被判过期。已让仅在测试中编译的 `test_support.rs` 使用现有 `spawn_replay`，并把该端到端用例改为固定历史时间，逐帧检查无异常。生产交易工作线程的系统时间门槛和超时没有修改；仍须重新跑完整双平台验收。
