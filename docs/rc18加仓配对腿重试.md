# rc.18 开仓/加仓配对腿滑点递增

本版仅提供 Windows x64 实盘包，版本 `0.2.0-rc.18`。两个标的、两个方向及 live/paper 使用同一执行核心。

## 新行为

正常开仓/加仓仍先在 Entropy 成交，再在 Lighter 配对，首次使用原配置滑点（当前 0.01%）。如果 Lighter 已明确结束但尚有未成交数量：

1. 先等至少 3 秒，再重新核对两平台的真实持仓、挂单和账本。
2. 只对差额尝试，滑点依次为 0.02%、0.03%、0.04%、0.05%，最多四档。每笔使用独立订单编号，发送前先持久化。网络和核对耗时会使实际间隔超过 3 秒。
3. 每次都使用新盘口，保留最低开仓价差、保证金、名义金额、数量精度等限制。若某一档没有足够合规深度，不发不合规订单，等下一档；价格改善才可能成交。
4. 0.05% 仍没配齐，进入原有减仓补偿：保留可以配成完整共同数量单位的部分，撤回剩余单边数量。若 Lighter 零碎成交不符合双平台共同精度，则按原规则先撤回本次 Lighter 成交，再撤回本次 Entropy 成交，不动更早的持仓。

停止交易、暂停、亏损保护、紧急全部平仓，或保证金/数量等风险条件不满足时，不再继续增加配对腿持仓，转入适用的减仓/紧急处理。行情无效不会被当成可交易报价；持续无法取得有效报价时放弃加仓补单，进入原减仓处理。账户或订单不确定时只核对，不能凭猜测再下一笔。

初次开仓和已有仓位上的加仓共用这套补单逻辑。正常平仓、减仓补偿的 0.02%～0.05% 重试、紧急全部平仓 5% 和连续三次回滚保护保持原规则。一次操作里的四档补单不算四次回滚；配对成功不计回滚，实际进入撤回后仍按原规则计数。

## 重启和诊断

重试档位、等待时间、累计已成交数量、订单编号都写入账本，重启不会清零重试档位。已有订单状态未知时，始终只查询原编号；不能因为过了 3 秒就再发单。旧版已在进行中的订单/撤回不会被重新解释成新的加仓补单。正常升级须先停止并处理完 pending；升级后新产生的开仓/加仓自动使用新规则，无需修改旧配置。

一键诊断新增 `pending.entry_hedge_retry`，包含当前档位、下次核对时间、是否已放弃补单和原因；保留每次请求编号的脱敏关联与数量。短暂重试成功不通知，长期未解决仍按现有异常通知规则提醒。重试提高了尝试成交的机会，不保证交易所必然成交或没有损失。

## Windows 升级

1. 把新 ZIP 解压到全新的 `CPA-rc18` 文件夹，暂不运行新 EXE。
2. 在旧程序分别停止 OPENAI、ANTH，运行旧目录的 `Run-Diagnostics.cmd`。确认两对都已停止、无 pending、无挂单、无孤立仓位，实际持仓与账本一致。有正常配对持仓可以升级；还有未完成订单时先发诊断，不能直接退出或复制账本。
3. 点击一次“退出后台程序”，确认后台退出。备份旧程序旁整个 `data` 文件夹。
4. 将整个 `data` 复制到新文件夹中的 `Cross-Platform-Arbitrage.exe` 旁，避免形成 `data/data`。不要用模板覆盖原配置，也不要只复制数据库。
5. 打开新 EXE，运行下面的只读检查；版本应为 rc.18，数据目录应指向新目录，提交号应与包内 `build-info.json` 一致。

   ```powershell
   $h = Invoke-RestMethod 'http://127.0.0.1:18794/health'
   [ordered]@{version=$h.version;commit=$h.build.source_commit;runtime=$h.build.runtime;data_dir=$h.data_dir} | ConvertTo-Json
   ```

6. 解锁两个标的及飞书，加载原账户和账本，先保持停止。核对原组数、两边数量、无 pending；有连续回滚保护时，须先用“核对并解除连续回滚保护”，不要手改账本。
7. 行情、账户、均线预热正常后，分别启动策略。运行新目录的 `Run-Diagnostics.cmd`，将生成的 ZIP 发来验收。新版出现新成交后，不可直接用旧备份覆盖当前账本。

## 验证

使用合成数据验证两标的、两方向、逐档成功/失败、部分成交及共同精度、重复回执、未知订单、重启、账户核对、价格预算、停止/风险控制和写盘失败；另运行原策略、签名参考向量、前端、Windows PowerShell 5.1 诊断和无凭据安装包启动检查。Windows live/paper 必须使用相同核心与决策轨迹。测试不接真实账户、不下真实订单。
