# rc.8：Entropy 未知补偿单的恢复

rc.7 的一条恢复路径会把已确认属于前腿的成交也当成未知补偿单的阻碍：查询窗口固定从补偿单创建前 5 分钟开始，只要窗口里有同标的成交，就无法证明补偿单未成交。这会使首腿成交、配对提交前被价格保护拦截、补偿结果超时的操作持续停在需要处理状态。

## 修复

- 共享执行流程在查询原订单时传递持久化账本证据；账户安全封装也完整转发该证据。没有新增下单入口，没有修改订单 ID、账本格式、仓位或规则迁移。
- Entropy 返回 `unknownOid` 仍不能直接视作拒单。仅在签名有效期结束并经过 30 秒、链上时间新鲜、没有该标的挂单、链上数量与账本完全相同、窗口内成交逐笔匹配已确认的其他订单时，确认原请求零成交并终结。
- 成交匹配包含完整成交标识、方向、时间、数量、价格、手续费。原请求已有部分成交、未知成交、缺少已知成交、数据冲突、重复记录、跨市场证据、仓位不一致都继续阻止重试。
- 成交历史使用未按 DEX/标的过滤的原始响应。达到 2000 条上限时拒绝推断历史完整性，避免过滤后误判空窗口。依据：[Hyperliquid Info 文档](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint)。签名过期依据：[Exchange 文档](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint)。
- 确认零成交后，仍由原有受控恢复流程核对两边新鲜账户，按已有退避间隔提交新的、仅减仓的补偿单。保护价格、数量上限和仅处理本次多出仓位的约束保留。
- Entropy 的只读账户预检有独立且短于外层执行期限的超时。如果尚未进入签名发送阶段，明确记录为未提交。进入发送阶段后的超时仍查询原订单，不能盲目重发。

30 分钟同价加仓间隔、5U 网格、每阶段最多 5 次、滑点、收益规则、账户绑定、飞书配置保持不变。Mac 与 Windows 使用同一份 Rust 策略核心；Mac 不启动模拟服务或实盘账户。

## 验证

新增合成证据用例覆盖两个标的、两个方向、4 小时及 24 小时后的已知历史成交，缺失/重复/未知/部分成交、原请求成交、满页历史、错误市场与请求、过期链上证据、错误数量及未发送预检超时。

完整恢复用例通过实际账户安全封装和共享执行流程，保存并重新打开 SQLite 账本，覆盖启动恢复及后台超时查询。旧 7 组仓位保持不变，原未知单不重发；零成交得到证实后只提交一次新的补偿单，保留停止状态、网格额度和最近开仓时间。最终由交易所回报的成交完成配平，不根据仓位差伪造成交。

发布验收还包括 Mac/Windows 两模式测试、签名向量、前端回归、Windows 无凭据启动检查和四份核心/规则/决策报告对比。

## 当前异常实例的更新原则

这是保留原有待核对订单的程序修复，不执行策略规则或账本格式迁移；常规升级仍要求停止且没有未决订单。

1. 把新 ZIP 解压到新的空目录，先不启动。核对发布清单中的版本和 SHA256。
2. 分别停止两个标的的新交易。用只读状态确认正常标的已停止且没有未决操作；异常标的须保留原 pending、成交和仓位记录，确认旧请求已经过期、两边无挂单、账本逐边与账户数量一致。
3. 原程序的退出按钮会拒绝带未决订单退出，不能清空 pending 绕过。只有上一步证据核对完成后，才按现场指导结束经过路径及 PID 确认的旧后台进程。
4. 确认后台进程和监听端口都退出后，备份整个旧目录，再把完整 data 复制到新 EXE 旁。包含可能存在的 SQLite WAL 文件；不能只复制单个 sqlite，也不能用配置模板覆盖账户设置。
5. 打开新版并核对 build-info。先解锁、只读检查；加载 ANTH 账户和原账本会启动原订单核对，并在充分证据下执行仅减仓恢复，即使策略仍保持停止。
6. 核对两边真实数量、账本和原有持仓组数；pending 消失、挂单为零、数量匹配后再考虑启动策略。若出现新未知成交、账户不一致或证据缺失，保留现场继续检查，不能手工修改账本。
7. 实际发生恢复成交后，旧备份不能再当作当前账本恢复交易。

升级按现场反馈逐步进行，不要求用户一次性执行以上全部步骤。修复恢复路径不等于跨平台成交具备原子性，也不能保证交易所断网或证据不可用时自动完成配平。
